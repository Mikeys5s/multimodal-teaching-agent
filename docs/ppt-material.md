> **宁可放过、不可误杀** —— 因为**误杀一个真知识点比留一个垃圾名更糟：前者看不见，后者看得见。**
>
> **而"看得见"之后由人裁决** —— 复核队列现在有 200 条待处理。
> **这就是我们说的『AI 干粗活 + 人做裁决』**：AI 不假装自己判准了，
> **它把不确定摊在界面上，由人收口。**」

**⭐⭐ 为什么改成这样**：

| | 旧说法 | 新说法 |

| 数字 | 629 是"知识点数" | **629 是"候选条目数"，167 个不同内容** |
| 风险 | 评委点开看到 `There`、看到同一个标题连排 4 次 → **信任塌一次** | 主动说"没去重、全标了存疑" → **它是防御机制的证据** |

**⭐ 三件必须先讲清的事**（不讲会被追问，讲了是加分）：

**① `200` 是"前端展示上限"，不是"图只有 200 个"。**

`GET /api/knowledge-graph` 有 `max_nodes` 参数（默认 200，可选到 1000），
**按 `seq` 截断，边只保留两端都还在的** —— 否则前端会画出指向不存在节点的悬空边。

**② `cycle_count = 0` 是在**完整图**上算的，不是截断后的结果。**

这一点很重要：`verify()` 拿的是完整图。
**⭐ 所以这个 0 不是"恰好没出错"，是"检查过的 0"。**

**③ `conflict_count` 的名字容易误导 —— 它的含义是「AI 抽出但还没经人确认的边」。**

```python
conflict_count = sum(1 for e in rows if e.needs_review == 1)
```

**625 = 全部抽取边 → "都还没被人复核过"** —— 演示库确实还没做过人工复核。

**⭐ 这一条要主动讲**（接口的 description 里已经写明了）：

> `pruned_count` / `conflict_count` 的存在，说明这个 `cycle_count = 0`
> **是「检查过」的结果，不只是恰好没出错。**

**环数 0 也可以独立复算**（两个来源，不只是接口自述）：

1. **接口**：`GET /api/knowledge-graph` → `stats.cycle_count = 0`
2. **确定性算法**：`skills/xizhi-graph-infer/scripts/graph_infer.py verify`
   （纯标准库，**不调用任何模型**）

**答辩话术**：「**图必须无环**这件事我们当成了工程不变量 ——
写库前校验、违规直接剪枝，**不是"我们希望它无环"，是"它不可能有环"。**」

**⭐ `seq=1001` 这条有个故事可以讲**（**体现"规格即法律"**）：

> SPEC §5.2 第 3 条要求「`seq` 在一个会话内单调递增，**跨轮次不重置**」。
> 我们**第一版是每轮从 1 开始**的 —— P3 用两轮实验抓到了（第 1 轮 id 1..6、第 2 轮又从 1 开始）。
>
> **根因**：`start_seq = 1` 只在客户端带 `Last-Event-ID` 时才改，
> 而**正常第二轮不带它** → 又回 1。
>
> **修法**：`start_seq = 学生轮序号 × 1000 + 1` ——
> 于是首轮从 **1001** 开始、第二轮从 **1003** 开始，**天然单调且可预测**。

**答辩话术**：「`seq` 不只是个序号 —— 它是**断线续推**的依据。
跨轮重复会让前端恢复到错误的轮次。**这种细节不写测试就只是文档里的一句话。**」

## 2. 技术方案的"取舍表"（可直接做成 PPT 的一页）

> **做 PPT 的人常犯的错**：只讲"用了什么"，不讲"**为什么不用那个更好的**"。
> 而**取舍**才体现判断力。

| 决策 | 选了什么 | **为什么不做那个更"标准"的** |
|---|---|---|
| 后端框架 | **FastAPI** | Stage 1 解析生态在 Python（PDF/OCR/PPTX 全在 Python）—— **换任何别的语言都要重写解析** |
| 数据库 | **SQLite（WAL）** | 单机、单用户、无并发写 —— **上 Postgres 是给自己加运维** |
| 向量检索 | **NumPy 暴力余弦 + FTS5** | 629 个知识点，**暴力算只需毫秒**；引向量库要付出索引构建 + 依赖体积 |
| 异步 | **BackgroundTasks + 任务表** | **不引 Celery/Redis** —— 单机任务量不值得多两个中间件 |
| 图可视化 | **自研纯 SVG + 自研 DAG 分层布局** | 见 §3（**这是 D-01，SPEC 已按此更正**） |
| LLM 调用 | **构建期用平台，运行期零外部依赖** | 赛事要求 LearnBuddy 为唯一平台 —— **我们让关键路径根本不需要 LLM** |
| 音频 | **不做** | 砍掉的理由写在 SPEC §6.1 —— **做窄通道会击穿"幻觉率为 0"的红线** |

**⭐ 最能讲的一条是最后一条**：

> **"我们不是能做的都做了，是知道哪些做了会坏事。"**
> 音频那条：ASR 错识别会让**溯源引用的原文本身就是错的** ——
> 那会**击穿我们的红线**。所以不做，并在 SPEC 里留了决策记录。

## 3. D-01：图可视化（**已拍板，可直接讲**）

| 项 | 内容 |
|---|---|
| **SPEC 原文** | 「图可视化 \| `Cytoscape.js`（DAG）」—— 两处（冻结表 + D6 任务） |
| **实际实现** | **自研纯 SVG 画布 + 自研 DAG 分层布局**，`cytoscape` 依赖不存在 |
| **处置** | **方案 A：改 SPEC 承认自研**（美佳拍板） |
| **理由** | 自研布局能讲「**最长路径分层 + 重心排序压交叉**」，**比"用了某个库"更有技术含量** |

**自研布局的算法（可直接讲）**：

1. **Kahn 拓扑序做最长路径分层** —— 层号 = 所有前置层号最大值 + 1，入度 0 落第 0 层
2. **层内重心排序**（下扫 4 轮 + 上扫 4 轮）压交叉
3. **层 → x**（左→右即先修在前），层内序号 → y

**⭐ 而且我们保留了"发现不一致并记录"的过程**（`docs/spec-diff-log.md`）：

> 那份文件开头写着：
> 「**先记事实与证据，再决定改代码还是改文字。**
> 不允许『反正能跑，就不记了』——
> **评委手里同时有 `SPEC.md` 和代码，文字与实现打架，比实现简单更减分。**」

**答辩话术**：「我们自己做了 SPEC 与实现的差异审计，**发现了一处并走了变更流程**。
这件事本身说明我们的**规格管理是真在跑的**。」

### 5.1 🚨 `hard_edge_count = 0` —— 一个**必须修**的缺陷

**已开 Issue `#103`。**

**现象（实测，不是读代码推断）**：

```
图上 196 条边：{'soft': 196}          ← 一条 hard 都没有

gap-analysis → hard_prerequisites: []
               likely_gap: null
               suggestion: "「…」没有 hard 前置，**它本身就是起点知识点** ——
                            卡点就在它自身"
```

**而那个知识点实际有一条 soft 前置** → **这句建议是错的**。

**根因（两行写死的代码）**：`structural.py:372` 与 `:388` 都写死 `relation_type="soft"`，
而 `graph_infer.py:56` 的默认值是 `HARD`。

**影响**：**"卡点根因回溯"正是主创新点第三块 ——
修好之前，PPT 里不要拿它举例。**

**为什么之前没被发现**：**验收指标里没有一条检查"hard 边是否存在"**。
`B1-2 环数 = 0` / `B1-5 边理由完备率 = 100%` / `A2-1 结构完整率 = 100%` **全绿**，
**但没有一条问「你设计了两类边，那两类都在吗」。**

> **⭐ 建议补一条验收指标**：`hard 边占比 > 0`（或"两类边都有样本"）。
> 否则这类"**设计了两类、只实现了一类**"的问题永远测不出来 ——
> 这是「指标真空满足」的又一个变体。
