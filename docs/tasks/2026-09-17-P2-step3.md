### 2.4 两条测试：这是"冻结"真正的保障

## 3. 需要你拍板的 5 件事

### 3.1 分支从哪起？
见 §1.3。**推荐：先把三个 PR 合掉，从 `main` 开 `feat/api-contract`。** 顺序必须是 skeleton → core-models → hardening（后两个基于前一个）。

### 3.2 ⭐ mock 做到什么深度？

| 选项 | 说明 | 取舍 |
|---|---|---|
| A · 纯 stub | 每个端点返回固定 JSON，不做任何校验 | 最快；但 P3 无法验证错误分支，且冻结的 schema 没被真实数据"跑"过 |
| **B · 校验真实 + 业务 mock（推荐）** | **输入校验按规格真实实现**（参数范围、格式白名单、文件大小、id 存在性→404、任务冲突→409），**业务数据返回 mock** | 多花约 1.5 h；但错误码与校验行为在冻结时就固化，P3 能完整对接 |
| C · 顺便把只读端点做真 | 读得出来的（health、capabilities、列表空数据）走真实现，写操作 mock | 介于两者之间 |

**我推荐 B**。理由：接口冻结的价值**主要在错误分支上** —— 正常路径 P3 一眼能看懂，
但"参数越界返回什么""id 不存在返回什么"才是 PM 前端时最容易对不齐的地方。
而且校验逻辑（格式白名单、大小上限）本来就与业务无关，现在写和 D2 写成本一样。

### 3.3 `/api/health/pragma` 怎么办？

- **补充进规格**（升为第 28 个端点，推荐）—— 它让"pragma 真的生效了吗"变成可验证的接口，演示时可用
- 或者**删掉**，把它降级成只读 `/api/health` 响应里的一个字段

**推荐补充进规格。** 删掉会损失一个"不假设、只验证"的展示点。

### 3.4 非 JSON 响应（markdown / CSV）怎么承载 `request_id`？

**推荐**：非 JSON 端点用 **`X-Request-ID` 响应头**承载；出错时仍返回 JSON 包封（Content-Type 切回 `application/json`）。
这样"报错时统一包封"的约定不被破坏，P3 的错误处理逻辑只有一套。

### 3.5 第二批 8 张表是否提前到本步之前？

见 §1.2。**推荐提前**（约 1 h），理由是"同一份字段定义两次"是错位高发区。
若时间紧，也可以不提前，但要在 schema 文件里写明"需与 `data-model.md` §2.6/2.7 对齐"，并在建模型时回头核对。

## 4. 验收方式

**做完的标准（逐项可验）**

- [ ] `docs/api-spec.md` 的 6 处缺口已补，版本号 v1.2 → v1.3，SPEC §12 有变更登记
- [ ] `GET /docs` 列出 **28 个**端点（27 + pragma），每个都有完整的请求 / 响应 schema
- [ ] `test_api_contract.py` 通过 —— **端点集合与规格一致**（这是冻结的自动守卫）
- [ ] `test_api_smoke.py` 通过 —— 每个端点可达、包封正确、错误码正确
- [ ] `pytest` 全绿、`ruff check` / `ruff format` 全绿
- [ ] **GitHub Issue 已发**：骨架冻结通告 + "只允许新增、不允许改已有字段"
- [ ] SPEC §9.2 的 I-3 标记为已完成

**注意**：验收不看"业务是否实现"，只看**契约是否冻结且自洽**。
所以"mock 数据看起来假"是正常的，"某个端点返回 404 而不是 200"才是缺陷。
