## 决策 1 · P1 的抽取修复**要不要重跑数据**

### 事实（**全部实测**）

```
线上现状：**629** 条知识点
按 name/summary 去重后：**167** 个不同内容
**462 条是副本**（73.4%）

⭐ 副本**跨"章段"**的证据（抽 `The next issue`）：
    kp_42b16cd4_000_000_006
    kp_42b16cd4_001_001_062
    kp_ada1063f_000_000_064      ← **另一份材料**
    （**同一个内容，出现在 4 个不同的"章段"里**）

⭐ 而 id 的 (章段, 节段) **只有 4 种取值**：
    (000,000)=213 · (001,001)=197 · (002,002)=126 · (003,003)=93
   ⇒ 那 4 个数字**不是章号、是材料序号**（4 份材料）——
   ⇒ **完全印证 P1 说的「id 的章段恒等于节段」**
```

### ⚠️ 而**这里有个我必须说清的歧义**

**"462 个副本"有两种可能的解释，而它们是**完全不同的问题**：**

| 解释 | 含义 | 该怎么处理 |
|---|---|---|
| **甲** | **抽取 bug 的产物**（同一批块被多个节各抽一遍） | **重跑修掉** |
| **乙** | **材料本身的真实重复**（4 份材料里有相同内容） | **保留 + 标注**（**我们现在的做法**） |

**⚠️ 而我**现在无法单靠数据区分这两者** —— 因为：
**id 的章段恒等于节段（那个 bug）** ⇒ **我们看到的"跨章"可能是假象**。

**⇒ 所以结论是**：**要区分它们，只能**实际重跑一遍到副本环境，看数字变成什么**。**
**⇒ 而那恰好就是我这次要建议的"先量后决"做法。**

---

### 三个方案

#### A · **不重跑**（保持 629）

| | |
|---|---|
| ✅ | **零风险、零工时** |
| ✅ | 我们对外讲的「**462 副本、只做标注不去重**」**画面上能看到、逻辑自洽** |
| ⚠️ | **根因没修** —— 若评委追问「这些副本是怎么来的」，**我们答不上"这是 bug 还是材料本来如此"** |

#### B · **重跑**（数字预计 ≈ **167**）

| | |
|---|---|
| ✅ | **数据干净、根因闭环**，且**能回答"462 是怎么来的"** |
| ⚠️ | **"462 副本"这个叙事就没了** —— 凡讲这个的 PPT/视频页都要改 |
| ⚠️ | **⚠️ 工时 2–3 小时**（重跑 pipeline + 重新灌库 + 复验） |
| ⚠️ | **⚠️ 而最大的风险：kp_id 会变** ⇒ **我已灌的 22 条例题 + 15 条误区会变孤儿**（要重新映射） |

#### ⭐ C（**我推荐**）· **先在副本环境试跑一次，看数字，再决定**

| | |
|---|---|
| 做法 | **不动线上** —— 在容器里跑一遍 pipeline 到一个临时库，**看 629 会变成多少、副本是否消失** |
| ✅ | **拿到事实再决定**（而不是凭推测） |
| ✅ | **风险为零**（线上不动） |
| ⚠️ | 工时 **~40 分钟**（比 A 多，比 B 少） |
| ⭐ | **而且它本身就是 B 的第一步** —— 如果结果好，直接接着做 B；不好，就回到 A |

**⇒ C 的额外好处**：**它能回答"那些副本到底是 bug 还是材料真实重复"** ——
而这**影响的不只是数字，是我们对外的话术**（说"标注"还是说"已修"）。

---

### ⭐ 我的推荐：**C**

**理由**：
1. **离 10/13 只剩 3 天**，"试跑 40 分钟"的成本**远低于**"猜错了再返工"
2. **它同时回答了话术问题** —— 那个比数字更要紧
3. **它是 B 的前置**，做了不浪费

**⚠️ 而如果时间不够（比如 P1 也在忙）**：**选 A** ——
因为**"标注不去重"本身是个成立的做法**，只是**根因留在那里**。

## 决策 2 · 部署从 5 分钟变成 46 分钟

### 事实

```
改前（单一源 阿里云）：构建 ~5 分钟 · **但缺包就直接失败** ⇒ 静默跑旧代码
改后（双源 阿里云+官方）：构建 **46 分钟** · **不会因缺包而挂**
```

### 三个方案

| 方案 | 做法 | 时间 | 风险 |
|---|---|---|---|
| **A · 保持现状** | 双源 | **46 min** | 无（**慢但稳**） |
| **B · 调 pip 参数** | 双源 + `--retries 2 --timeout 15` | 预计 **~15 min** | 低（**重试少了，但双源还兜着**） |
| **C · 只留官方源** | `PIP_INDEX_URL=https://pypi.org/simple/` | **不确定**（国内可能很慢） | 中（**官方源在国内不稳**） |

### ⭐ 我的推荐：**A（保持）**

**理由很实际**：
- **离截止 3 天**，**部署慢是"等待"，部署失败是"事故"**
- 46 分钟**可以并行干别的**（我这几轮就是在等部署时写的文档）
- **B 看起来更优，但它需要再验证一次**（调完参数得跑一遍看是不是真的 15 分钟）
  ⇒ **又是一轮 46 分钟的风险**

**⚠️ 而如果部署变成瓶颈**（比如要连着部署 3-4 次）：
**那时再上 B** —— 但**别在交付前最后一次部署前改**。
