## 二、⭐ 一个新增风险（P3 报告里没有，我今早才看到）

**515 个知识点里，大量名字是垃圾。**

今早那次抽取泄漏出真实的名字：

```
CHAPTER          FIVE          END-TO-END PROTOCOLS
Victory          —Winston Churchill          Many technologies can be used
```

**根因**：`extract/structural.py` 的 `_name_from_block` 是**纯结构线索**（定义句式 + 首句截断），
遇到"章标题""引语署名""页眉残留"都会当成知识点名。
模块 docstring 里其实**诚实记账过**这一点（「抽出来的 name 会偏长、偏口语」），
但**没人预见到会抽到"Winston Churchill"**。

**为什么这条要紧**：
- 演示时点开知识点 → 看到人名/页眉 → **比 mock 还难看**
- 它是 `/graph` `/path` `/tutor` **三页的可见内容** —— 而现在这三页"有数据了"，正好会把它暴露出来
- **它和 `/outline` 的修法是同一个地方**（都靠真实 blocks 推导）

## 五、建议（三个方向 + 我的推荐）

### 方案 A：产品优先
先把 P0 四条 + P1 三条全做完，再动交付物。

**好处**：产品最完整，"可演示"最强。
**风险**：**交付物 4 项在 9/22 之前可能一件都没有** —— 而 9/22–23 是要提交保底版的。
**如果产品临期出问题，就没有可交的东西了。**

### 方案 B：交付物优先
先保五件套（草稿版），产品做到哪算哪。

**好处**：9/22 一定能交一版，压力小。
**风险**：**视频里六页只有两页能演**，评委会看出产品没做完。

### ⭐ 方案 C：并行（**推荐**）
**产品侧一天一条，内容侧同时推进**，两条线各走各的。

**为什么推荐**：
1. **两条线互不依赖** —— 脚本/PPT/对话记录**不需要产品做完**就能起稿
2. **风险对冲** —— 万一产品卡住，交付物已经有实物；万一交付物卡住，产品已经很能演
3. **符合 P3 的做法** —— 他已经准备了保底方案（Stage 1 真实 + Stage 2/3 预置），**并行正是这个方案的执行方式**
4. **9/22 的保底版**需要两边都有东西，A/B 都只有一边
