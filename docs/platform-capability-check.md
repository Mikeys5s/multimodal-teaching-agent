## 3. 核心算法实测记录

### 3.1 算法清单

`graph_infer.py`（纯 Python 标准库，零第三方依赖，零模型调用）：

| 命令 | 算法 | 对应验收项 |
|---|---|---|
| `verify` | 图完整性校验：环检测 / 稀疏性 / 理由完备率 / 自环 / 孤立节点 | **B1-2**、**B1-5** |
| `prune` | 环路检测与剪枝（Kahn + DFS 三色找环 → 按 confidence 升序剪边 → 软删除留痕 → 剪后复核） | **B1-2** |
| `path` | 学习路径（沿 hard 边反向可达 + Kahn 拓扑排序） | **B1-3** |
| `gap` | 卡点根因回溯（反向可达 + 三层启发式排序，全部可解释） | **B1-6** |

### 3.2 真实数据实测（用冒烟测试的抽取产出）

| 项 | 结果 |
|---|---|
| 输入 | `samples/channel-smoke-test/P10-output-with-nodes.json`（9 个知识点 + 10 条边） |
| **环数量** | **0** ✅ |
| 理由完备率 | **100%**（10/10）✅ |
| 稀疏性 | 合规（最大入度 3 / 出度 3，上限为 3 / 4）✅ |
| 起点知识点 | 拥塞窗口 CongestionWindow（唯一无前置）✅ |

**学习路径实测**（目标 = 快速恢复 Fast Recovery，共 4 步，拓扑有序）：

```
1. 拥塞窗口 CongestionWindow        ← 起点
2. 加性增 Additive Increase          ← 依赖 1（公式分母是 cwnd）
3. 慢启动 Slow Start                 ← 依赖 1（"翻倍"翻的是 cwnd）
4. 快速恢复 Fast Recovery            ← 依赖 2（收尾回到加性增）+ 依赖 3（删掉那段慢启动）
```

**卡点回溯实测**（同样目标，未传误区）：

```
你这一题卡在「快速恢复 Fast Recovery」，但根因更可能是「拥塞窗口 CongestionWindow」没吃透
—— 建议先回去补它，再回来学目标知识点。

依据：距目标 2 层依赖（断层较深）+ 后续有 3 个知识点依赖它（关键地基）
```

### 3.3 对抗性测试（顺便成了 B1-4 的测试夹具）

| 用例 | 构造内容 | 期望 | 实际 |
|---|---|---|---|
| **T1** `T1-single-cycle.json` | 唯一三元环 A→B→C→A，其中 C→A 的 confidence 最低 | 剪掉 C→A，剪后环数 0 | ✅ 完全符合，且列出了环上全部候选边及其 confidence 供审计 |
| **T2** `T2-adversarial-composite.json` | 环 + 自环 + 缺 reason + 稀疏性违规（Z 有 4 条入边），四类问题一次性 | 四类全部检出并处理 | ✅ 检出 4 类；剪枝 2 轮（先剪环、再剪自环）；剪后环数 0、自环 0；**缺 reason 的边被保留为待人工处理项，未被剪枝掩盖** |

> T2 的最后一句话很关键：**剪枝不会把"缺理由"这类问题一起掩盖掉** —— 它只处理环，其他问题原样报出，交给人判断。

## 4. 本轮实测发现的 6 个问题

### ① 平台已有能力相近的 Skill（`courseweaver-knowledge-structurer`）

平台预置了一个 `courseweaver-knowledge-structurer`：输入教材文件，输出「章—节—知识点」三级结构 + 难度 + **前后依赖关系** + 知识图谱 HTML 页面。

**对我们的影响（两面）**

| 正面 | 风险 |
|---|---|
| **可视化模板可直接借鉴**（它生成了树形 + 图谱双视图的自包含 HTML，省掉我们前端画图谱的工时） | 需要看清差异：**它的依赖是"章级"的**，没有 hard/soft 边语义、没有 reason、没有环路校验、没有学习路径与卡点回溯、没有原文溯源 |

**结论**：我们的创新点仍然成立且区分明显。**但可视化部分应该先看它的模板再动手** —— 能省则省（建议 2 人时）。

### ② 图只包含"出现在边里的节点" —— 孤立知识点会被漏掉

只传 `edges` 时，没有任何边的知识点**根本不会进入图**，`isolated_nodes` 永远是空的。

**实测证据**：只传 edges → `node_count: 7`、`isolated_nodes: []`；补上 P4 的 9 个节点全量列表后 → `node_count: 9`、**`isolated_nodes` 检出 2 个**。

**规范要求**：入库流水线**必须把 P4 的知识点全量列表一并传入**（用 `nodes` 字段）。已加入 §4 落地建议。

### ③ 真实冒烟数据里确实有 2 个孤立知识点（且原因清楚，不是缺陷掩盖）

| 孤立知识点 | 原因 | 处置 |
|---|---|---|
| **快速重传 Fast Retransmit** | 它依赖的是「重复 ACK」这个概念，而该概念在冒烟抽取中**没有被抽成独立知识点** —— 属于**真实的漏抽** | 补抽「重复 ACK」节点，或把它并入快速重传的 `summary_md` 后补 soft 边 |
| **拥塞窗口与通告窗口取小** | 它的边在 `deferred_edges` 里（跨章依赖，等第 5 章节点入库后补） | 已在 P10 契约的 `deferred_edges` 中登记，属**已知待补** |

> **这就是"孤立节点必须显式列出"这条规则的价值**：它把"看起来没问题"变成了"两个具体待办"。如果只看"环数 0"就收工，这两处会一直潜伏到演示当天。

### ④ 发现并修掉一个真 bug（`depended_by_count` 数错了度数方向）

首版卡点回溯里，`depended_by_count` 用的是**入度**（该知识点有多少前置），而语义要的是**出度**（有多少知识点依赖它）。导致「关键地基」这一层依据从未生效。

**修正**：改用出度。**这个 bug 只有拿真实数据跑一遍才会暴露** —— 看代码是看不出来的。

### ⑤ 项目内预装了一批技能（但多为 Android/Node.js 方向）

`D:\muti_tagent\skills\` 下有 30+ 个预装技能。筛选后**真正可能用上的**：

| 技能 | 用途 | 适用度 |
|---|---|---|
| `frontend-patterns` | React / 状态管理 / 性能优化 | ⭐ 可直接用（我们前端是 React） |
| `frontend-design-direction` | 前端设计方向与美学原则 | ⭐ 可用于 UI 打磨 |
| `code-reviewer` | 代码审查 | ⭐ 对应 SPEC §9.3 的合并前 review |
| `tdd-workflow` / `testing-setup` | 测试工作流 | ⭐ 对应 A4-1（单测覆盖率 ≥60%） |
| `pdf` | PDF 处理 | 可参考（Stage 1 用 PyMuPDF，未必需要） |
| ~~`backend-patterns`~~ | Node.js / Express / Next.js | ❌ **不适用**（我们是 FastAPI/Python） |

### ⑥ Skill 的"代码双位置"问题

Skill 里的脚本在 `~/.learnbuddy/skills/`（用户级），而**源码交付要进项目仓库**。两者若不处理会各改一份、逐渐漂移。

**处置见 §5**。

## 5. D1 落地建议

| # | 建议 | 理由 |
|---|---|---|
| 1 | **代码以项目仓库为准**：把 `graph_infer.py` 纳入仓库（建议 `pipeline/graph_infer.py`），Skill 目录内**只保留一份副本并在 SKILL.md 头部注明"源文件在仓库 X 处"** | 避免双份漂移；源码仓库是必需交付物 |
| 2 | **Skill 目录一并进仓库**（放在 `skills/xizhi-graph-infer/`），并在 README 说明如何安装回本机 | 让评委能看到"这个能力是怎么挂到平台上的" —— 这本身就是混合形态的技术证据 |
| 3 | **入库流水线必须传 `nodes` 全量列表**（见问题 ②） | 否则孤立知识点永远检不出来 |
| 4 | **写单测**：把 T1 / T2 两个对抗性用例固化为 pytest 用例 | 一举两得：既做 B1-4 的验证材料，又撑 A4-1 的覆盖率 |
| 5 | **先看 `courseweaver-knowledge-structurer` 的 HTML 模板再动前端图谱** | 可能有现成的双视图实现可借鉴，省工时 |
| 6 | MCP 形态**暂不做**（除非 Skill 形态遇到瓶颈） | Skill 已验证够用，MCP 需要你手动信任且收益不确定 |
