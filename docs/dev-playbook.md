## 2. 干活的顺序

```
读 SPEC 相关章节
  → 看 Issue / PR 现状（别人可能已经在做，或已经定了口径）
  → 契约优先：先确认数据结构 / 接口 / 字段语义，再写实现
  → 写测试（尤其"坏数据"的测试，不只是"正常路径"）
  → 写实现
  → 自查：ruff + pytest + git status
  → PR（关联 Issue）→ 至少 1 人 review → 合并
```

**第 2 步最容易被跳过，代价最大。** 今天有两次差点重复劳动：
`backend/tests/` 的归属、`ParsedSection` 的区间语义 —— 都是"先看现状"能避免的。

## 3. ⚠️ 环境坑规避（本机实测，全部踩过）

### 3.1 工作区文件会被成批删除 —— 未定责（Issue #20）

**现状**：本机有程序在删文件，已发生 5 次。`git restore .` 能救（文件都在 git 里）。

**每次 `switch` / `checkout` / `commit` / `merge` 之后，先 `git status` 一眼。**
看到一片 ` D` 就 `git restore .` —— **成本 2 秒**。

> **最危险的场景**：在"文件已被删、还没恢复"的状态下继续写代码并提交 ——
> 那会把删除结果**固化进历史**。

**另外**：`.git/refs/heads/*`（刚写的松散 ref）也会被删 →
**分支不推进**，而 `git commit` 的输出看起来完全正常。详见 Issue #20。

### 3.2 原生 Windows 程序要 Windows 路径

**规律**：**原生 Windows 程序**要 `C:/...`；**bash 内建与 MSYS 工具**才认 `/c/...`。

**已踩的 5 个实例**：

| 命令 | 传 POSIX 路径的后果 |
|---|---|
| `python -m venv /c/x/y` | **静默建不出** `Scripts/python.exe` |
| `ssh-keygen -f /c/Users/...` | `Saving key failed` —— **而目录明明存在** |
| `powershell -Command "... '/d/foo'"` | 建到了 `D:\d\foo` |
| `scp /d/... host:...` | `No such file or directory` |
| `git -C /c/...` | `cannot change to '...'` |

**共同点：报错信息指不到真正原因。**
问自己一句：**这个程序是原生的还是 MSYS 的？**

### 3.3 别把命令输出吞掉再判成败

```bash
ssh-keygen ... > /dev/null 2>&1 && echo "已生成"     # ← 实际什么都没生成，白跑一轮
```

**失败路径要看得见。** 判成败之前先让输出出来。

### 3.4 别给 bash 脚本接管道

```bash
docker compose build 2>&1 | tail -30      # ← 输出被缓冲，构建跑 19 分钟一个字看不到
```

**改成写文件、事后再读**：`docker compose build > /root/build.log 2>&1`，然后 `tail` 日志。

**同类**：`pwsh -Command ... | head` 也会被 Bash 过滤器吞掉输出（见 `dev-environment.md`）。

### 3.5 禁用 `git rebase`

**P1 实测：`rebase` 会让 `.git/refs/` 整个目录消失，稳定复现 2/2，仓库直接不可用。**

同步 main 一律用 `merge`。

### 3.6 本环境 bash 缺常用命令

`sleep` · `seq` · `chmod` · `od` · `cygpath` 都没有。

**替代**：等改用 `python -c "import time; time.sleep(n)"`；循环用 `while [ $i -lt N ]`。

### 3.7 国内网络：pip / npm / Docker 都要配镜像源

| 用什么 | 坑 | 修 |
|---|---|---|
| **Docker 拉镜像** | `registry-1.docker.io` **直连超时** | 配 `/etc/docker/daemon.json` 的 `registry-mirrors`（本地实测差 **500 倍**） |
| **pip** | **"通"但慢到像卡死**（13 分钟没跑完） | `PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/` → **30 秒** |
| **npm** | 同理，包多更明显 | `NPM_REGISTRY=https://registry.npmmirror.com` |

> **「通」和「快」是两回事。** pip 那个坑最阴：进程 CPU 54%，
> **看起来像在编译，其实不是** —— 让人往错方向查了很久。

### 3.8 TLS 证书问题**每台机器不一样**

- 有人的症状是**卡 90 秒后 `server closed abruptly`** → `http.sslBackend=openssl` 有效
- 有人是 **`CRYPT_E_NO_REVOCATION_CHECK`**（吊销列表查不到）→ openssl 也不通，
  只能作用域限定地关校验：`git config --global http."https://github.com/".sslVerify false`

**先看错误码再选方案**，别当"网络波动"忍。

## 4. 提交纪律

| 场合 | 规则 |
|---|---|
| 分支 | `git switch main` → `git pull --ff-only` → `git switch -c feat/简短任务名` |
| 命名 | `feat/` `fix/` `docs/` `test/` `chore/` |
| 提交信息 | 「类型 + 简短说明」，**不加 `[P1]` 前缀**（人员归属由 commit author 记录） |
| 流程 | **一律走 PR**，至少 1 名队友 review 后合并 |
| 同步 | `merge`（**不是 rebase**）；个人分支用 `--force-with-lease` |
| 已共享的提交 | 用 `git revert`，**不改写公共历史** |
| 提交前 | 必跑 `git status` + `git diff --staged`（禁 `.env` / Key / 隐私） |
| **频度** | **每完成一小块就提交推送** —— 本机环境不稳，**攒着不推是风险** |

## 5. 写代码时的三个自问

1. **这个错了会有人知道吗？** —— 如果答案是"不会"，那你需要一条断言或一个测试
2. **我的"完成"有证据吗？** —— 测试通过？命令输出？**没验证过的"完成"不算完成**
3. **换一份数据/换一个人跑，还成立吗？** —— 硬编码阈值、本机路径、私货依赖，都要问这一句

## 7. 改**已有文档**之前，先看一眼它的格式

### 为什么单独列一条

2026-09-19 一天之内因为这件事错了两次，**两次都是「动手前没看」**：

| 我做了什么 | 实际格式 | 后果 |
|---|---|---|
| 往 `api-spec.md` §7 追加 3 行端点 | §7 是 **5 列**（`# / 方法 / 路径 / 所属 / 阶段`） | 我插了 3 列的行 → **解析器读不到** → 契约测试红 |
| 用半段替换改一个测试函数 | 函数后半还有断言 | **留下孤儿断言** → 多跑一轮 |

**两次都不是「不会写」，是「没先看」** —— 而「看一眼」的成本是**一条命令**。

### 机械化

```bash
# 往表格里加行之前：先看表头
grep -n '^|' docs/api-spec.md | head -5

# 改一个函数之前：先看它的完整范围
grep -n '^def <名字>' -A 40 path/to/file.py
```

**一句话：在动一段已有结构之前，先用一条命令确认它的形状。**
猜形状的代价远高于看一眼。

### 附带一条：替换要整段，不要半段

半段替换（只匹配函数的前半）**会静默留下孤儿代码** ——
编译器与 shell 都不会报错，只有测试或运行时才暴露，而那时你已经多花了一轮。
**要么整函数替换，要么按行号整段删除。**

### 还有一条：写脚本改文件时，字符串里的引号要小心

同一天，我写「往文档里追加一段中文」的脚本时，**脚本自己因为中文里夹了半角引号而语法错**
（`SyntaxError: invalid syntax. Perhaps you forgot a comma?`）——
于是那次操作**一行都没写进去**，而我还以为改了。

**规矩**：脚本里的中文内容**统一用「」**，不要用半角双引号。
改完**立刻跑一次**确认真的写进去了（`grep` 一下那行）。

## 8. 写检查工具：**先写夹具，再写检查**

> 顺序反了，你就只会验证「我以为的输入」，验证不了「真实的输入」。

### 为什么单独列一条

2026-09-19 我在**检查工具本身**上错了 7 次，全是同一件事：
**检查不可靠，却输出「通过」**。

| 错法 | 表现 | 后果 |
|---|---|---|
| 漏检 | 正则只抓到 14/21 条调用 | **照样打印「完全对得上」** |
| 结论写死 | 7 项过了 6 项，结论句还是「仍被拦」 | 让人误判环境状态 |
| 误报 | 前缀匹配把前端路由当成「拼错的接口」 | 让人去查不存在的问题 |
| 测试写错 | 跨盘测 `sed -i` 报 `EXDEV` | **差点把「测试错了」记成「环境坏了」** |

**这一整天我在评审里抓的就是这个毛病** ——「自我实现的断言」「真空满足的指标」——
**结果自己在同一个坑里摔了七次。**

### 机械化：三条规矩

**① 先写夹具。** 一个「故意写错」的输入文件（放 `samples/`），
让检查跑它，**要求它必须报**。不报 = 这个检查是坏的。

```bash
# 例：scripts/check-api-parity.py --selftest
# 样本：samples/parity-probe.ts（故意写错的方法、不存在的路径）
```

**② 结论必须从数据推导，不能写死。**

```python
# 坏：不管发生什么都打印同一句
print("删除/改名仍被拦，git 不可用")

# 好：从失败项推导
if not rename_ok:  print("改名不可用 -> git 必然失败")
elif not git_ok:   print("改名可用但 git 仍写不了 —— 这是另一个故障")
```

**③ 抓取要「抓宽」，不要「抓准」—— 抓少了才是灾难。**

想精确抓「接口调用」-> 漏检；改成「把所有以 `/` 开头的字面量全抓出来」-> 全覆盖。
**抓多不值钱（多出来的人来筛），抓少才是灾难。**

### ⚠️ 合成用例验证不了扫描器

这是最容易被忽略的一点：

> **合成数据只能验证「比对逻辑」，验证不了「扫描器本身」。**

我写契约比对时，合成用例全过，**而扫描器里有两个真 bug**
（`${}` 没归一化、方法前瞻越界）—— **是扫真实夹具才抓到的**。

所以：**测「处理器」要用真实数据，测「逻辑」才用合成数据。**

### 已有的样板

- `scripts/check-api-parity.py --selftest` —— 8 个用例（3 合成 + 5 扫夹具）
- `scripts/gate-selftest.sh` —— 在克隆副本里注入故障，证明 `gate.sh` 的闸会 FAIL
  （当前 ①② 已证明；③④ **未证明，脚本如实报出**）

## 9. ⭐ 遇到问题：先找根因，不打补丁

> **同一处改到第 2 遍，就停手问根因。第 3 遍一定是错的。**

这一条是 2026-09-20 用一整天 8 次同类错误换来的，**不是原则宣讲，是可执行判据**。

### 9.1 先看那 8 次是怎么发生的

| # | 现象 | 我当时做的 | 真正该做的 |
|---|---|---|---|
| 1–7 | 「改了没」判断错（7 次！） | 每次都**改那个字符串** | 换工具：用 `Edit` 的匹配检查 |
| 8 | 「轮 2 返回空」 | 去查轮 2 的代码 | **先看原始输出** —— 是我自己的 grep 把它滤掉了 |

**⭐ 8 次全是同一个形状**：

> **我用「自己写的检查」替代了「工具自带的检查」。**

- **改文件** → 该用 `Edit`（内置"必须精确匹配、否则报错"），**我却写 Python 脚本自己判断**
- **看结果** → 该看原始输出，**我却加了一层自己写的过滤**

**打补丁 = 把「这次的结果」改对。找根因 = 问「我为什么会用这个方法」。**

### 9.2 四条可执行判据

**① 同一处改第 2 遍 → 停手。**

不是"这次小心点"，是**这个方法有问题**。
第 2 遍之后要问的**不是**「哪里又错了」，而是「**我为什么需要再改一遍**」。

**② 改文件：优先用工具，不要自己实现"改了没"。**

| 场景 | 用什么 |
|---|---|
| 改一处已知内容 | **`Edit` 工具** —— 不匹配就报错，天然可靠 |
| 改完要确认 | **读回真实值**（`Read` / `sed -n 'X,Yp'` 看**那一行的上下文**） |
| ❌ 绝不要 | 用「全文里有没有这串字」判断「这一处改了没」 |

**③ 看结果：看原始输出，不加自己的过滤。**

2026-09-20 的实例：输出命令里带了 `grep -vE "...|    "` ——
那个 **4 个空格**会删掉任何含 4 空格的行，而结果行有 `{path:<44}` 的填充空格 → **全被滤掉**，
于是我以为「功能没工作」，**实际是我的观测手段把它删了**。

**要过滤就 filter 已知的噪声前缀**（`grep -vE "httpx|INFO"`），
**不要 filter"看起来像格式"的模式**。

**④ 硬编码的字面量：从源头读。**

```python
# ❌ 硬编码 —— 问题不在于"这次写错了"，而在于**它总会过期**
source_type="pdf"                       # 合法值是 "pdf_text"，撞 CHECK 约束

# ✅ 从源头读
from app.models._common import SOURCE_TYPES
source_type=SOURCE_TYPES[0]
```

枚举值 / 常量 / 路径 / 白名单 —— **凡是"另一处也定义过"的东西，都不要抄第二份。**

### 9.3 判据：我是在打补丁还是在修根因？

一个问题问自己：

> **「如果换一个人、换一份数据、或者下周再看，这个修法还成立吗？」**

- **成立** → 修的是根因
- **不成立**（只对这次的数据/这次的字符串/这个具体的值有效）→ **是补丁**

| 打补丁 | 修根因 |
|---|---|
| 把 `pdf` 改成 `pdf_text` | 从 `SOURCE_TYPES` 读 |
| 把这个判断的字符串换个写法 | 改用工具自带的匹配检查 |
| 给这个 case 加一个 `if` | 问「为什么需要这个 `if`」 |
| 再过滤一次输出 | 看原始输出 |

### 9.4 一处只对 8 次里的第 8 次成立的补充

**出问题时，先分清「是被测对象错了」还是「我的观测手段错了」。**

今天的统计：**8 次里，至少 4 次实际是观测手段的问题**（判据不对齐、过滤把结果删了）。
而**我每一次的第一反应都是去查被测对象**。

**先问一句**：**「我怎么知道我看到的是真的？」**
