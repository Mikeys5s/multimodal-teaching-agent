## 三、本日最值得记下的方法学

**① 「成批删除」要分两类 —— 判别方法与处置完全不同。**
看到工作区一片 `D`，先分类，别一上来就查删除工具：

| 类别 | 特征 | 会丢东西吗 | 怎么处置 |
|---|---|---|---|
| **A. 删除工具主动删** | 有 `genie-trash` 日志；`.venv` / `node_modules` / `.git/objects/pack` 也中招 | **会真丢** | 查删除工具 |
| **B. 半次 git 操作被中断** | 删除范围恰好等于某个 commit 的目录结构；`.git/objects/` 完好；内容还在 HEAD 里 | 不会（`git restore` 就回来） | **先查 `index.lock`，不要查删除工具** |

今天这次落在 **B** —— 这也是我判断它「不是 #20 复现」的依据。

**② `index.lock` 判据修正：只观察「还在不在」会误判。**
**每次失败的 git 命令自己会留下一个 0 字节锁** —— 删掉后看它回不回来，等于在看自己的脚印。
**正确判据：删掉后立刻再跑一次需要写 index 的命令** —— 通过 = 陈旧锁；又报 `File exists` 且 mtime 是刚刚 = 有进程在反复创建。

**③ 一个主题一次「游离 HEAD」。**
PR #87 意外多带 4 个文件（`+461 / files=5`，我只想提 1 个文档），根因是**在同一个游离 HEAD 上连着提交两次**（提交①抽屉 → #86，提交②文档 → #87），于是 #87 的历史里带着 #86 的提交。
**处理**：先合 #86，#87 的 diff 会**自动收敛为只剩 1 个文档**（Git 不重复合入已进 main 的提交）。
**正确做法**：**每个主题一次游离 HEAD，做完一个就 `git switch --detach origin/main` 回到干净点。** 注意 —— 游离 HEAD 提交流程本身**有效**（两次都「提交落地 = True」、无孤儿提交）；**错的不是方法，是复用了同一个点。**

**④ 把风险变成「会拦下我的动作」，而不是「记得小心」。**
写 `.py` 时在 ASCII 双引号里夹了半角双引号（`w("... "反复回来" ...")`）→ `SyntaxError`，**脚本一行没跑**（今天第 4 次，且是当天读到 #58 模式 C 当天又犯）。
**机械拦截**：**写完任何 `.py` 先 `python -m py_compile <file>`，通过才运行。** —— 这就是 `docs/dev-playbook.md` §9 说的「**有没有一条命令能挡住它**」：不靠「记得用「」」，靠「编译不过就跑不起来」。
