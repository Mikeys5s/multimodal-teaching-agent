> 上游文档：[`../SPEC.md`](../SPEC.md) §2.3 / §4.7 / §8
> 版本：v1.1 · 2026-09-17

| 决策 | 结论 | 落到 SPEC |
|---|---|---|
| 作品形态 | **混合形态**（LearnBuddy 专家智能体 + 自建 Web Demo） | §2.3 S8、§6 D-16 |
| **部署** | ⚠️ **必须做轻量部署，提供稳定可访问链接** —— v1.8 曾误判为"不买主机"，**v1.9 已修正** | §4.7 |
| 预算 | **¥0 ~ ¥79**（学生券后可能仍为 ¥0 ~ ¥10） | §6.2 |
| 工时 | 专家智能体 5 人时；部署 6 人时；总额仍 185 | §8.1 |
| 排期 | **D5 部署上线（硬要求）**；D8–D9 专家智能体配置与上线 | §8.2 |

### ⚠️ 为什么要修正：手册书面要求优先于口头口径

| 来源 | 说法 |
|---|---|
| **手册 §二（书面，评审依据）** | 「作品须**部署至浏览器环境**，提供**可直接访问的在线链接**；须提交完整的源代码仓库；需提交 LearnBuddy 历史对话记录」—— **必需材料** |
| 赛事方（口头） | 「提交 demo 即可，**不用部署到正式环境**」 |

**两条不矛盾**：口头口径降低的是**门槛**（不用域名备案、不用生产级运维、不用 SLA、不用负载均衡），**不是要求本身**。

| | 可接受 | ❌ 不可接受 |
|---|---|---|
| 部署形态 | 轻量主机 2 核 2G 单容器跑着，公网 IP 直接访问 | 只用 cloudflared 临时隧道或本地运行 |
| 后果 | 满足"可直接访问的在线链接" | **评委评审期点开 404，等于没有链接** |

> 下文 §1 ~ §6 保留为决策依据与提问清单。§6 的问题仍建议问（尤其第 3 个：平台能力边界），但已不阻塞决策。

## 1. 这句话确认了什么、又留下了什么

### 1.1 已经确定的（可以直接据此调整）

| # | 变化 | 影响 |
|---|---|---|
| 1 | **不强制部署到正式环境** | 云服务器、域名、备案、HTTPS、容器化这些"正式环境"工作**可以不做**。这是原计划里风险最高的一环（R-01 / R-05） |
| 2 | **LearnBuddy 上的智能体本身就是作品形态** | 作品不一定是"我们自己写的 Web 应用"，也可以是在平台上配置的智能体 |
| 3 | **允许"web demo"这一形态** | 自建 Web 应用仍然被认可，只是不要求上正式环境 |
| 4 | **交付的核心是"能跟它交互体验"** | 评价方式从"点开一个链接看"变成"跟智能体交互"——**这恰好是我们的强项（答疑辅导天然是交互式）** |

### 1.2 还没确定、**必须去问**的（见 §6）

- "不用部署到正式环境"是否意味着**提交材料里也不需要链接**？
- "专家智能体"形态的**工程完整性（25%）如何评分**？有没有最低技术要求（比如必须提交代码仓库）？
- LearnBuddy 平台是否支持**挂载自建服务 / 自定义 Skill / 外部接口**？

> ⚠️ **这三个问题不确认清楚就不能定形态。** 但可以先做一件不受影响的事：**把抽取产物（知识点 + 依赖图）构建好** —— 无论最终选哪种形态，这份结构化数据都是底座。

## 2. 三种作品形态方案

### 方案 A · 纯 LearnBuddy 专家智能体

在平台上配置一个「计算机网络学习辅导」智能体：角色设定 + 知识库（我们离线抽好的知识点与依赖关系）+ 对话策略。

| 维度 | 评估 |
|---|---|
| ✅ 优势 | 零部署、完全符合赛事预期、评委即开即用、开发成本极低（约 1–2 天） |
| ❌ **致命劣势** | **核心创新点全部做不出来** —— 依赖 DAG 的环路校验与剪枝、学习路径拓扑排序、卡点根因回溯、苏格拉底状态机的"代码层强制降级"，**这些都是纯 Fig 算法与状态机，平台配置无法承载** |
| ❌ 工程完整性 | 没有代码仓库可看，"前后端分离 / 数据库 / 单测覆盖率"这些实证项全部落空 → **25% 那项几乎拿不到分** |
| ❌ 技术创新性 | 只剩 Prompt 设计，容易被判定为"套壳"（而手册 §8.3 明确禁止"AI 生成完整方案后直接提交"） |
| 结论 | **不推荐作为唯一形态** |

### 方案 B · 纯自建 Web Demo（当前 SPEC 方案）

| 维度 | 评估 |
|---|---|
| ✅ 优势 | 创新点完整可实现、工程完整性拉满、完全可控 |
| ❌ 劣势 | 需要一个"能体验"的交付方式（"不用正式环境"降低了门槛，但没说不需要）；"AI 工具使用 25%"的举证要额外做 |
| 结论 | 可行，但**放弃了"专家智能体"这条赛事项明确认可的低成本路径** |

### 方案 C · 混合形态 ★推荐

**LearnBuddy 专家智能体做"入口"，自建 Web Demo 做"深度"。**

| 形态 | 承担什么 | 为什么是它 |
|---|---|---|
| **LearnBuddy 专家智能体** | 答疑对话入口；基于我们离线构建的知识库回答问题 | 对话式交互天然适合答疑；评委零门槛；**开发期使用记录本身就是提交材料** |
| **自建 Web Demo** | 素材工作台、知识图谱可视化、依赖 DAG、学习路径、卡点根因回溯、人工校验工作台 | 这些**必须是图 + 界面**，对话形态表达不了 |

**为什么这是推荐方案**

1. **两个形态各自解决对方的短板**：专家智能体解决"可交互体验"，Web Demo 解决"技术深度可被看见"。
2. **我们的架构天然支持这种拆分**。SPEC §4.8 已定为「**离线构建 + 在线零模型依赖**」—— 知识已经结构化落库，**喂给平台知识库是零改造成本的**。
3. **工时几乎是净减少的**（见 §4）：因为省掉了正式部署，腾出的时间正好覆盖专家智能体的配置。
4. **两类评分项都被覆盖**：技术创新性 30%（Web Demo 的图算法）+ 工程完整性 25%（Web Demo 的代码与测试）+ AI 工具使用 25%（专家智能体 + 对话留痕）+ 用户体验 20%（两条线都是）。

**关键设计：两者如何分工不重复**

```
┌─────────────────────────────────────────────────────────┐
│  LearnBuddy 专家智能体（入口层 · 零门槛）                  │
│  · 学生提问 → 基于我们构建的知识库作答                     │
│  · 目录/知识点检索式问答                                  │
│  · 引导语：想看到知识图谱与学习路径，请打开 Web Demo       │
└───────────────────────┬─────────────────────────────────┘
                        │ 共享同一份离线构建产物
                        ▼
┌─────────────────────────────────────────────────────────┐
│  自建 Web Demo（深度层 · 展示技术含量）                    │
│  · 素材工作台 · 知识图谱（依赖 DAG）· 学习路径             │
│  · 苏格拉底式答疑（★ 代码层强制降级状态机）                │
│  · 卡点根因回溯 · 人工校验工作台 · 质量报告                │
└─────────────────────────────────────────────────────────┘
```

> **重要**：**苏格拉底式答疑的"代码层强制降级"必须放在 Web Demo 里做主实现**。它是我们最硬的一条设计原则（SPEC §5.3 R3：「降级由代码层强制，不依赖 LLM 自觉」）。放一份轻量版到专家智能体做入口引流即可 —— 但 **PPT 里要讲清楚哪边是主实现**，不要让人以为我们只会写 Prompt。

## 3. 成本与工时的变化

### 3.1 省钱

| 项 | 原预算 | 新预算 | 说明 |
|---|---|---|---|
| 云服务器 | ¥38 ~ ¥68 | **¥0**（若确认无需链接）或 ¥0~20（临时按量） | 不再需要长期主机 |
| 域名 | ¥1 | **¥0** | 同上 |
| **合计** | ¥39 ~ ¥69 | **¥0 ~ ¥20** | 模型费用本来就是 ¥0（§6.2） |

### 3.2 省工时（也是风险释放）

| 项 | 原工时 | 变化 | 说明 |
|---|---|---|---|
| 正式部署（容器化 + 上线 + 调试） | 6 | **−6** | 原计划 D5 的硬里程碑压力解除 |
| **新增**：专家智能体配置与调试 | — | **+7** | 角色设定、知识库接入、对话策略、测试 |
| **新增**：轻量演示通道（临时隧道或本地录屏） | — | **+2** | 用临时隧道可在演示时提供链接，无需长期主机 |
| **净变化** | | **+3** | 约 3 人时，可从缓冲里出 |

> **最大的收益不是省时间，是释放风险**：原计划里 R-01（时间不够）与 R-05（云服务器踩坑）是两条高影响风险，现在**基本消失**。D5 那个"硬里程碑"也可以松绑 —— 它本来就是为"必须上线"这个假设设的。

### 3.3 风险变化

| 风险 | 变化 |
|---|---|
| R-01 前后端分离 + 数据库做不完 | **显著降低**（少一个部署环节） |
| R-05 云服务器购买踩坑 | **基本消失** |
| R-07 评委现场上传材料导致演示翻车 | **进一步降低**（专家智能体用预置知识库，天然不会翻车） |
| **新增 R-19** | **形态判断错误** —— 如果赛事方其实要看代码仓库，而我们只做了平台智能体；或反之。**缓解：先去问清楚（§6）** |

## 4. 对交付物的影响

手册 §4.1 要求的五项交付物，逐一评估：

| 交付物 | 原方案 | 新方案 |
|---|---|---|
| 作品链接 | 公网正式部署地址 | **待确认**。可能是 ① 平台上的专家智能体页面 ② 临时隧道地址 ③ 不需要 |
| Demo 视频（3min） | 必需 | **必需不变**。而且"不用正式环境"后，视频的分量更重了 —— 它可能是评委看到 Web Demo 深度的**主要途径** |
| 介绍 PPT | 必需 | **必需不变**。**新增一页"作品形态说明"**，讲清专家智能体与 Web Demo 的关系 |
| 源代码仓库 | 必需 | **必需不变**。**这恰恰是我们保住"工程完整性 25%"的关键** —— 无论形态怎么变，代码仓库都不能省 |
| LearnBuddy 使用记录 | 必需 | **必需不变，且分量上升**。专家智能体形态下，这份记录本身就是作品的一部分 |

> **结论：源码仓库与 Demo 视频一个都不能省。** 它们是"工程完整性"与"技术深度"的唯二证据。

## 6. 必须去问赛事方的四个问题（可直接复制）

> 你好，想确认几个关于初赛作品形态的问题：
>
> 1. **作品链接**：手册 §4.1 里「作品链接：可直接在线体验的地址」是必需材料。如果初赛不用部署到正式环境，那这一项现在是否还需要？如果需要，是**评审期间必须一直可访问**，还是**提交时能给一个可体验的地址即可**（比如本地演示 + 录屏）？
>
> 2. **专家智能体形态的评分口径**：评分表里「工程完整性 25%（代码质量、架构设计、功能完备性）」这一项，对于**纯平台配置的专家智能体**如何评价？是否仍需要提交完整的源代码仓库？
>
> 3. **平台能力边界**：LearnBuddy 上搭建智能体时，是否支持**挂载自建服务 / 自定义 Skill / 调用外部接口**？我们有一个基于图算法的知识依赖分析模块，想确认能否与平台智能体打通。
>
> 4. **形式可以混合吗**：我们的设想是「平台上做一个专家智能体作为交互入口 + 自建一个 web demo 展示知识图谱与学习路径可视化」，这种组合是否符合赛事预期？

## 7. 我的建议（一句话版）

> **走方案 C（混合形态）：用 LearnBuddy 专家智能体做零门槛入口，用自建 Web Demo 承载全部技术创新；正式环境部署可以不做，但源码仓库、Demo 视频、LearnBuddy 使用记录三样一个都不能省。**
>
> **同时立刻去问 §6 的四个问题** —— 尤其是第 1 和第 2 个，它们直接决定形态选择。

**不因形态变化而改变的东西**（这些是我们的地基）：

1. **核心创新点必须有代码承载** —— 依赖 DAG 环路校验、学习路径拓扑排序、卡点根因回溯。没有代码，技术创新性 30% 与工程完整性 25% 同时落空。
2. **苏格拉底式答疑的"代码层强制降级"不能妥协** —— 这是 SPEC §5.3 的硬规则，也是我们区别于"套壳聊天"的核心。
3. **离线构建 + 在线零模型依赖的架构不变** —— 它本来就适配任何交付形态。
