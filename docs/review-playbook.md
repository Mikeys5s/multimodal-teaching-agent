# 验收与风险审查清单

> **本文是「验收」这件事的单一来源。** Skill `xizhi-review` 只是它的薄封装 ——
> 内容改这里，不改 skill。
>
> 配套工具：**`../scripts/gate.sh`（交付门，一条命令跑完四道闸）** ·
> [`../scripts/review-verify.sh`](../scripts/review-verify.sh)（独立克隆里跑测试）
> 相关：[`CONTRIBUTING.md`](../CONTRIBUTING.md)（协作规范） · [`delivery-checklist.md`](delivery-checklist.md)（交付物盘点）

## 0. 交付门：每次交付必须过四道闸

**团队要求（2026-09-19 定）**：**每次交付不仅要"能跑通"，还要通过测试脚本、并严格按验收标准验收。**

```bash
bash scripts/gate.sh          # 当前工作区（提交前自查）
bash scripts/gate.sh --pr 41  # 独立克隆里验某个 PR
```

| # | 闸 | 查什么 | 不过是哪类问题 |
|---|---|---|---|
| ① | **ruff** | 代码层面 | 代码有问题 |
| ② | **全量测试（含端到端链路）** | 行为层面 | 有东西坏了 |
| ③ | **假数据审计**（`audit-mock-endpoints.py`） | **数据是不是真的** | **测试全过，但功能是假的** |
| ④ | **验收指标**（`evaluate.py --strict`） | 按 SPEC 的可测标准 | 指标没达标 |

### ⚠️ 为什么 ③ 必须单独设一道闸

**因为"测试通过"和"功能是真的"是两件事。**

本项目的真实记录：**400+ 测试全绿，而 10 个端点返回硬编码的假数据。**
测试全过、界面有数据、接口返回 200 —— **而数据是编的**，端到端从未跑通。

**根因**：所有测试都是在"有 mock 数据"的假设下写的。它们验的是**契约形状**，
**没有一条问过"空库上这个端点该返回什么"。**

### 为什么做成一条命令，而不是三条要求

三项要求分开写会**退化成一句口号** —— 人在赶时间时总会挑着做（通常挑最省事的那件）。
做成一条命令的意义不是省事，是**让它变成一个整体**：
**要么全过，要么全不过，没有"我只跑了测试"这个选项。**

### 端到端链路的「完成」定义

`backend/tests/test_e2e_pipeline.py` 是**链路是否接通的唯一判据**：
一份文件进去 → 一条学习路径出来，七步全通。
**它不依赖任何外部素材**（PDF 是程序化生成的），所以任何人都能跑。

它现在是 `xfail(strict=True)`，这个选择是刻意的：

- **现在它失败 → 不挡任何人**（"已知不通"被**显式记录**，而不是被遗忘）
- **链路接好后它一旦通过 → XPASS 会让测试套件变红** → **强制移除这个标记**

**不让"已知不通"变成"早就忘了"。**

### 0.1 交付门自带「工作区完整性预检」

跑门之前先检查 `git status` 里有没有 ` D`（工作区有文件被删但未提交）。

**这不是洁癖，是本机的必需**：本机有「文件被成批移走」的已知问题，
今天它发作过三次，最严重的一次 `scripts/` 下五个文件一起消失。
**不加这一步，门会在很后面报一个 `No such file or directory`** ——
看起来像"工具没装"或"脚本写错了"，而真实原因只是文件被移走了。

## 0. 为什么需要一份清单，而不是"看一眼代码"

因为**最贵的错不会报错**。

本项目一次 PR review 抓到 5 个缺陷，**没有一个会让测试变红**：

| 抓到的缺陷 | 如果不发现的后果 |
|---|---|
| 验收指标的取值路径漏了 `knowledge_points.` 前缀 | `_dig` 返回 `None` → **在满数据的库上也会误判 FAIL** —— 结论直接反了 |
| 用「期望值 ≤ 1.0」猜显示格式 | 环数（**计数**）被显示成 `0.00%` —— 读者以为在说比率 |
| catch-all 把 `/api/**` 吃掉了 | 前端调错接口拿到 HTML，在 `response.json()` 那行炸掉，**报错跟真正原因毫无关系** |
| entrypoint 自检用裸 `sqlite3.connect()` | 日志印「外键开关 : 0」而接口说 `1` —— **谁读日志谁往错方向查** |
| 覆盖率的分母可能与被测逻辑同源 | 指标**自我实现**，永远 100% |

**共同点：全部通过测试、全部不报错、全部会让人得出错误结论。**

所以验收的目标不是"代码写得好不好"，而是
**「这个结论可不可信、这个数字是不是真的、这个错会不会被藏起来」**。

## 1. 第一原则：**独立性**

> **绝不在主工作区里验收。**

两个理由：

1. **主工作区不可信** —— 本机存在"工作区文件被成批删除"的未定责问题（Issue #20，已 5 次）。
   在一个会随机丢文件的环境里跑测试，**你分不清失败是代码的问题还是文件又没了**。
2. **独立克隆能证明"别人跑得起来"** —— 本地有一堆 gitignored 的私货
   （`.learnbuddy/`、本机 venv、教材文件）。在作者机器上跑通**不等于**在别人机器上跑得通。

**做法**：`bash scripts/review-verify.sh --pr <n>`
它会克隆到项目之外、建独立 venv、**先做文件完整性预检**、再跑测试。
脚本还会断言 `import app` 解析到克隆内部 —— **防止"验错对象"这种最隐蔽的乌龙**。

## 2. 五类"最贵的错"（逐类检查）

### ① 静默错误 —— 不报错但结果错

**最贵的一类。** 检查方法：**问"如果这一步错了，会有人知道吗？"**

- 这个指标算错了，界面会显示异常还是显示一个"看着合理"的数？
- 这个字段取不到值（`None`）时，是报错还是静默当成 0 / 当成空？
- 这条分支走错了，日志里看得出来吗？

**实例**：`_dig(report, "structure_complete_rate")` 拿不到值返回 `None`，
而 `None == 1.0` 为 `False` → 判 FAIL。**它没有崩，只是把结论判反了。**

### ② 指标自我实现 —— 分子分母同源

**检查方法**：**分母（或阈值）是怎么来的？它独立于被测逻辑吗？**

**实例**：覆盖率的分母若用"解析器认为自己该抽的东西"来算，那永远是 100%。
本项目做对了 —— 分母来自 **PyMuPDF 原始文本 + bbox 判定**，独立于解析器的块输出。

**反向也要查**：有没有**上界**？只有下界的指标挡不住"同一段文字被抽两遍"。

### ③ 只在特定数据下成立的阈值

**检查方法**：**这个数字换一份输入还成立吗？**

**实例**：覆盖率分母里 `bbox.top < 60` / `> 730` 是**针对某一份 LaTeX 教材版式**的硬编码。
换一份 PDF（不同页高/页边距/字号）就不成立 →
**这个数字只在限定条件下有效，写进报告时必须标注前提。**

### ④ 边界与守恒

- **区间语义**：闭区间还是半开？边界元素归哪一边？
  （本项目实例：`ParsedSection` 的块区间差一个块就会让知识点挂错节 ——
  而"三级结构完整率 100%"是硬指标，**挂错不报错，只会让答案悄悄变错**）
- **空输入 / 全空 / 单项**：不崩吗？返回的语义对吗？
- **守恒**：进去多少、出来多少，对得上吗？

### ⑤ "真空满足" —— 全绿但没有意义

**检查方法**：**分母是 0 吗？**

**实例**：空库跑评估脚本，所有比率分母为 0 按定义返回 1.0 → **五项验收全 PASS**。
**这什么都没证明。** 必须造**真实的坏数据**（一个真的环、一个断链、一条非接地轮次）
去看指标**真的会变红**。

## 3. 核对"声明 vs 实现"

作者在 PR / Issue 里写的数字与结论，**自己跑一遍**。

- 他报「403 passed」→ 我在独立克隆里跑，数出 404 / 14 skip
- 他报「逐字忠实性 307/307」→ 这个测试**默认被跳过**（缺教材）→
  **意味着除他之外没人能复现** → 这本身就是一个要提的问题

**原则**：**"他说的"和"我验出来的"要分开写**，不一致就摆出来。

### 3.1 ★ 引用他人的数字做决策时，必须标注「几手数据」

**2026-09-18 的真实事故**（写在这里，因为它差一点进 SPEC）：

> 我基于队友给的「OCR 19.2 s/页」拍板了「20 页 ≤ 8 min」的门限。
> 那个数字是他在**一张 4 行小图**上量的 —— 真实密集扫描页实测 **140.4 s/页**（差 **7 倍**）。
> **门限从拍板那一刻起就是错的。**
>
> 最后是**他自己**在 OCR 链路实现完、实测一跑就发现不对，主动喊停：
> 「**8 min 这个数字请先不要写进 SPEC**」。
> **如果没有他这一喊，这个数字会一路传到答辩。**

**教训不是"他给错了"，而是"我不该拿一个未经复测的数字去推门限"。**

| 情形 | 必须怎么做 |
|---|---|
| 用**自己跑过**的数字 | 直接用，写明"我实测" |
| 用**别人报**的数字 | 标注它是**一手还是转述**，并写明**未复测** |
| 用它去**定指标 / 门限** | **先复测；做不到就把它标成"待复测"再定稿** —— 绝不能默默当已知量 |

### 3.2 ★ 门限只承诺「我们控制得住」的维度

同源的另一条经验：

- 「20 页扫描件的**总时长**」→ **不可控**（由内容密度 + 硬件共同决定）
  → 拿它当门限 = **承诺一个我们做不到的数** = 验收必红
- 改成「**单页 ≤ 3 min** + 异步 / 进度可见 / 可中断」→ 这三个**都是我们能保证的**

**判断方法**：写下这个门限时问一句 ——
**「如果达不到，是我们能修的，还是外部条件决定的？」**
后者不该写成门限，只能写成**参考值 + 前提声明**。

## 5. 输出格式

回报时**四块都要有**，缺一块就等于没验：

```
## 结论
   可合并 / 需修改（一句话，别绕）

## 我独立验证过的（我跑出来的，不是他报的）
   环境：独立克隆 + 独立 venv（路径）
   结果：ruff / pytest 数字 / 文件完整性

## 五类错的检查结果
   ①静默错误：…  ②自我实现：…  ③阈值限定：…  ④边界：…  ⑤真空满足：…

## 建议（标出哪些阻塞合并、哪些是后续）
```

**"我没查"也要明说** —— 不要用模糊措辞掩盖没查的部分。

## 6. 分工：脚本查什么，人查什么

| | 谁查 |
|---|---|
| 测试是否通过、静态检查、文件完整性、与 main 的差距 | **脚本**（`review-verify.sh`） |
| 上面五类错、声明 vs 实现、交付物影响 | **人** |

**脚本能把"环境问题"和"代码问题"分开，这是它最大的价值** ——
但**判断"这个错会不会被藏起来"只能靠人**。

---

## 7. 一条纪律

> **发现自己之前写的东西有同样的毛病，也要在评论里说出来。**

本清单里一半的例子是**我自己写的代码**。
验收的价值不在于证明别人错了，而在于**把"不报错的错"提前变成"可见的错"**。
